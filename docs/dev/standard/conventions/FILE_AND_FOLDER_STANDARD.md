# Стандарт файлов и папок

> Каноническое правило: **как организована файловая структура** в любом
> проекте, который собирает Архитектор.
>
> Читается до создания нового проекта или изменения структуры.

---

## 1. Принципы

1. **Один взгляд на корень.** В корне видны входы, документация, настройки,
   тесты, инструменты, изменяемое состояние и кодовый профиль.
2. **Код не смешивается с управлением проектом.** Для одиночного Python-проекта
   код живёт в `src/<package>/`, а корень остаётся картой проекта.
   Для больших существующих проектов и многомодульных репозиториев выбирается
   отдельный профиль, описанный в этом стандарте.
3. **Папка появляется по причине.** `llm/`, `browser/`, `plugins/`,
   `deploy/`, `build/` не создаются без реальной задачи.
4. **Изменяемое состояние отдельно.** `data/`, `logs/`, `artifacts/` не
   смешиваются с исходниками и не попадают в Git содержимым.
5. **Порядок и статус живут в документах.** Номера `NN_` и суффиксы
   `__STATUS` применяются к управляемым документам, а не к исходному коду.
6. **Точки запуска тонкие.** Запуск собирает зависимости и передаёт управление
   в сценарий. Бизнес-логика живёт ниже.

## 2. Единый корень

Базовый корень проекта:

```text
<project_root>/
├── README.md
├── AGENTS.md
├── CLAUDE.md
├── QWEN.md
├── ARCHITECTURE_AND_AGENT_STANDARD.md
├── structure.txt
├── pyproject.toml  # если в корне есть Python-пакет или Python-сервис
├── .gitignore
│
├── src/            # для одиночного Python-проекта
├── configs/
├── scripts/
├── tools/
├── tests/
├── docs/
├── data/
├── logs/
├── artifacts/
│
├── deploy/        # если проект разворачивается как сервис
├── build/         # если есть сборка поставки
├── .claude/
├── .qwen/
├── .cursor/
└── .opencode/
```

Назначение верхнего уровня:

| Путь | Роль |
|------|------|
| `README.md` | главный вход для человека: назначение проекта, главная команда запуска, карта проекта |
| `AGENTS.md`, `CLAUDE.md`, `QWEN.md` | входы для агентов |
| `ARCHITECTURE_AND_AGENT_STANDARD.md` | локальная копия или ссылка на общий стандарт |
| `structure.txt` | профиль структуры и фактическое дерево проекта |
| `pyproject.toml` | описание Python-проекта и инструментов, если Python-пакет живёт в корне |
| `.gitignore` | что не попадает в Git |
| `src/` | исходный код по профилю проекта |
| `configs/` | конфигурация запуска |
| `scripts/` | операторские разовые команды |
| `tools/` | инструменты разработки и проверки |
| `tests/` | тесты |
| `docs/` | документация по `DOCUMENTATION_STANDARD.md` |
| `data/` | изменяемое состояние, не хранится в Git |
| `logs/` | журналы выполнения, не хранятся в Git |
| `artifacts/` | результаты прогонов и временные выгрузки, не хранятся в Git |
| `deploy/` | материалы развёртывания, если нужны |
| `build/` | результаты сборки, если нужны |
| `.claude/`, `.qwen/`, `.cursor/`, `.opencode/` | настройки инструментов агентов |

Общий минимум для любого проекта:

```text
README.md
AGENTS.md или CLAUDE.md
structure.txt
.gitignore
docs/
docs/README.md
docs/ТЕРМИНЫ.md
```

`structure.txt` начинается с явной строки профиля:

```text
# Профиль структуры: `product_platform`
# Обновлено: YYYY-MM-DD

.
├── README.md
└── docs/
```

Профиль пишет агент при подключении проекта к стандарту. Если проверка
автоматически определила другой профиль, сначала разбирается причина: проект
действительно изменил природу или в `structure.txt` устарела запись.

Полноценный одиночный Python-проект дополнительно требует:

```text
pyproject.toml
src/
configs/
scripts/
tools/
tests/
data/
logs/
artifacts/
```

`deploy/` и `build/` создаются только при реальной потребности. Пустые
`llm/`, `browser/`, `plugins/` в корне не создаём.

## 2.1. Канонический запуск

В каждом рабочем проекте должна быть одна явно указанная главная команда
запуска. Она фиксируется в корневом `README.md` в разделе `Запуск`.

Если проект имеет несколько режимов, первым указывается обычный локальный
запуск, а остальные команды идут ниже:

```text
## Запуск

Основной запуск:
<command>

Дополнительно:
- тесты: <command>
- проверка: <command>
- сборка: <command>
```

Правила по типам проекта:

| Тип | Канон |
|-----|-------|
| Новый Python-сервис | внутренняя точка запуска `src/<package>/app/main.py`; корневая обёртка `run.sh`, `run.cmd` или `run.ps1` вызывает её без бизнес-логики |
| Python-пакет или библиотека без собственного процесса | команда `python -m <package>` или публичная команда из `pyproject.toml`; искусственная обёртка `run.*` не нужна |
| FastAPI/ASGI-сервис | команда запуска в `README.md`; ASGI-объект может жить в `src/<package>/app/main.py` или в файле, который требует фреймворк |
| Frontend | главные команды живут в `package.json`; в `README.md` указать `npm run dev`, `npm run build`, `npm test` или фактические аналоги |
| Многомодульный проект | у корня есть главная команда запуска проекта; у каждого сервиса или модуля может быть свой `README.md` с локальной командой |
| Переходный или старый проект | не переименовывать рабочие `main.py`, `start_server.py`, `run_project.sh`, если это ломает запуск; фактическую команду зафиксировать в `README.md`, миграцию описать в `docs/ТЗ/*__TODO.md` |
| Локальная утилита или один скрипт | допустим прямой запуск файла, например `python script.py`, если это указано в `README.md` |

`main.py` — не обязательное имя корневого файла. Для новых Python-проектов
каноническое место — `src/<package>/app/main.py`; корневые файлы запуска
допустимы только для маленьких утилит и переходных проектов.

### Паттерн канонического запуска `run.sh`

Для приложения унифицируются и смысл, и базовое имя файла запуска:

```text
run.sh       # macOS/Linux
run.cmd      # Windows cmd
run.ps1      # Windows PowerShell
```

Расширение зависит от операционной системы, базовое имя `run` — нет. Имена
`run_project.sh`, `run_8050.sh`, `start_server.sh`, `launch.sh` и `dev.sh` не
являются каноничными. При постепенном переносе `run.*` может временно вызывать
старый файл.

Шесть правил паттерна `run.sh`:

1. **Единая точка входа без параметров («Правило одного клика»):**
   Запуск локального контура проекта выполняется строго одной командой без флагов:
   `./run.sh`. Любые переданные параметры вызывают ошибку валидации и справку
   (код завершения 2). Скрипт не перегружается подкомандами (`start`, `stop`,
   `status`, `restart`). Управление жизненным циклом фоновых сервисов и демонов
   принадлежит оркестратору (`automation_server`), а не локальному run-скрипту
   конкретного репозитория.
2. **Foreground-only режим и подмена процесса через `exec`:**
   Скрипт запускается только на переднем плане: журналы сразу выводятся в
   терминал, остановка — стандартный Ctrl+C. Завершающая команда выполняется
   через `exec make run`: `exec` заменяет процесс bash-оболочки процессом
   приложения; сигналы ОС (`SIGINT`, `SIGTERM`) доставляются напрямую серверу
   без зависших промежуточных процессов-зомби.
3. **Автономность от активации виртуального окружения (`uv run`):**
   Скрипт не требует предварительного выполнения `source .venv/bin/activate`
   пользователем. Внутри скрипта запрещены хрупкие ручные вызовы активации.
   Вместо этого запуск делегируется в `Makefile`, где команды вызываются через
   `$(UV) run --locked ...`. Утилита `uv run` детерминированно находит `.venv`
   в корне проекта или использует активный `$VIRTUAL_ENV`.
4. **Автоматическая подготовка состояния перед стартом (Pre-flight миграции):**
   Запуск сервера (`run`) в `Makefile` всегда объявляется зависимым от миграций
   базы данных: `run: migrate`. Разработчику не нужно держать в голове
   `alembic upgrade head` — схема базы данных всегда актуальна на момент старта.
5. **Безопасный Dev-контур с автовходом (`<APP>_DEV_AUTO_LOGIN=1`):**
   В `run.sh` экспортируется флаг локальной разработки: `export CRM_DEV_AUTO_LOGIN=1`
   (или соответствующий префикс приложения). Сервер проверяет этот флаг в связке
   с адресом клиента: автоматический вход без токена разрешён только для loopback
   (`127.0.0.1` или `::1`). Внешние запросы и промышленный запуск остаются закрыты.
6. **Независимость от рабочей директории:**
   Скрипт определяет путь к корню своего репозитория и делает `cd`, поэтому
   корректно работает при вызове из любой папки файловой системы:
   ```bash
   PROJECT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
   cd "$PROJECT_DIR"
   ```

**Переопределение порта и настроек:**
Поскольку `run.sh` не принимает параметров командной строки, переопределение порта
и хоста выполняется через переменные окружения (`PORT=8085 ./run.sh`), файл
конфигурации или файл переменных окружения. В `Makefile` задаются значения по
умолчанию:
```makefile
HOST ?= 127.0.0.1
PORT ?= 8080
```
Приоритет порта: переменная окружения `PORT` > значение по умолчанию в `Makefile`
или файле конфигурации.

Эталонный код `run.sh`:

```bash
#!/usr/bin/env bash
set -Eeuo pipefail

PROJECT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
cd "$PROJECT_DIR"

if [[ "$#" -ne 0 ]]; then
  echo "Использование: ./run.sh" >&2
  exit 2
fi

# Экспорт флага локального dev-контура (только для 127.0.0.1)
export CRM_DEV_AUTO_LOGIN=1

# Подмена процесса: передача управления в Makefile без порождения висячих shell-обёрток
exec make run
```

В `README.md` раздел `Запуск` использует следующие глаголы:

| Глагол | `en_public` | Что делает |
|--------|-------------|-----------|
| `запуск` | `run` | обычный локальный запуск продукта |
| `тесты` | `test` | прогон тестов |
| `проверка` | `check` | валидатор структуры и линтеры |
| `сборка` | `build` | выпуск или бандл |

Если в репозитории несколько продуктов, глагол получает суффикс продукта:
`запуск (fns)`, `тесты (fns)`. Новые глаголы не выдумываются: задача, не
попавшая в таблицу, идёт в `Дополнительно:` списком.

### Канон точки входа

Раскладку файлов задаёт `ENTRYPOINTS_STANDARD.md`, и он здесь источник
истины:

```text
python -m <package>                 основная команда
src/<package>/__main__.py           или [project.scripts] в pyproject.toml
run.sh / run.cmd / run.ps1          единая операторская команда приложения
bin/<project-command>[.cmd|.ps1]    устанавливаемая публичная команда продукта
```

`scripts/` — это сценарии разработки, миграции и обслуживания, а не основной
пользовательский запуск. Различие `bin/` / `scripts/` / `tools/` описано в
`PROJECT_LAYOUT_STANDARD.md` §4.

Переименование рабочих `start_server.bat`, `run_project.sh` и подобных не
выполняется вслепую. Для перехода добавляется `run.*`, который вызывает старый
вход; фактическая команда `run.*` указывается в `README.md`, а удаление старого
имени описывается в `docs/ТЗ/*__TODO.md`.

Точка запуска должна быть тонкой:

1. прочитать конфигурацию;
2. проверить обязательные зависимости и переменные окружения;
3. собрать зависимости приложения;
4. передать управление сценарию или серверу;
5. не содержать бизнес-логику.

Агент перед запуском проекта обязан сначала найти раздел `Запуск` в
`README.md`. Если раздела нет, он не угадывает команду по файлам, а добавляет
или запрашивает явную команду запуска.

## 2.2. Каноническая сборка (`build.*`)

Для проектов, требующих компиляции, защиты кода через Cython или сборки
бинарных пакетов (PyInstaller, Electron), предоставляется единая команда сборки:

```text
build.sh       # macOS/Linux
build.cmd      # Windows cmd
build.ps1      # Windows PowerShell
```

Скрипт сборки поддерживает два режима работы:

1. **Автоматический режим (фоновый/headless):** запускается, если переданы
   аргументы командной строки или скрипт выполняется вне интерактивного
   терминала (`[ ! -t 0 ]`):
   - `--check-deps` — проверка наличия зависимостей и компиляторов (Python,
     Cython, Node.js, C-компилятор);
   - `--target-cython` — компиляция критических Python-модулей в C-расширения
     (`.so`/`.pyd`) с очисткой отладочных символов (`strip`);
   - `--target-binary` — упаковка в запускаемый бинарный файл (PyInstaller или Electron);
   - `--target-all` — полный конвейер сборки;
   - `--clean` — удаление временных файлов сборки.
2. **Интерактивный режим оператора:** если скрипт запущен человеком в интерактивном
   терминале без параметров, выводится меню с выбором действий цифрами.

Все промежуточные файлы сборки сохраняются строго в каталоге `build/`, а готовые
пакеты — в `dist/` (или `build/dist/`). Запрещено оставлять скомпилированные
бинарники в корне репозитория или внутри `src/`.

## 2.3. Политика распределения сетевых портов парка

Чтобы избежать взаимных конфликтов сервисов и не занимать стандартные порты
разработки, в парке действует регламент сетевых портов:

1. **Порт `8000` зарезервирован для локальной временной разработки и быстрых
   тестов (ad-hoc).** Ни один постоянный сервис парка не имеет права занимать
   порт `8000` в конфигурациях по умолчанию.
2. **Сетка выделенных портов парка:**

| Диапазон / Порт | Назначение | Сервисы парка |
|---|---|---|
| `8000` | Временная разработка и ad-hoc тесты | Локальный uvicorn/FastAPI, быстрые тесты разработчика (постоянным сервисам запрещён) |
| `8050..8059` | Сетевые сервисы и системные мониторы | `Network_AI` (системный трей и монитор: `8050`) |
| `8080..8089` | Бизнес-приложения и сервисные платформы | `CRM` (`8080` вместо `8000`), Service Desk (`8082`) |
| `8585..8599` | Центр автоматизации и оркестрация | `automation_server` (`8585`) |
| `8760..8799` | Когнитивные сервисы и базы знаний | `RAG` (`8765`), `IskInoSfera` (`8766`) |
| `8100..8199` | Динамический резервный пул (`fallback`) | Временный порт при конфликте, параллельные копии (`worktree`) |

3. **Правила для серверов автоматизации (`automation_server` / `server_control`):**
   - При запуске подчиненного процесса (`subprocess`) порт передаётся явно:
     `./run.sh --port <PORT>` и переменной окружения `PORT=<PORT>`.
   - Если базовый порт занят посторонним процессом, `automation_server` выделяет
     свободный порт из пула `8100..8199`, передаёт его в `./run.sh` и фиксирует
     фактический адрес в реестре состояния сервисов.

## 3. Профиль Python

Канонический Python-профиль:

```text
src/
└── <package>/
    ├── __init__.py
    ├── app/
    ├── core/
    ├── use_cases/
    ├── adapters/
    ├── models/
    └── utils/
```

Опциональные подпапки внутри `src/<package>/`:

```text
llm/       # если есть LLM-провайдеры
browser/   # если есть браузерная автоматизация
plugins/   # если есть расширения
```

Роли кодовых папок:

| Путь | Что можно | Что нельзя |
|------|-----------|------------|
| `src/<package>/app/` | запуск, сборка зависимостей, разбор аргументов | бизнес-логика, прямые запросы к БД/HTTP |
| `src/<package>/core/` | чистая доменная логика, алгоритмы, инварианты | импорты из `adapters`, `plugins`, `app` |
| `src/<package>/use_cases/` | сценарии работы, координация `core` и `adapters` | технические детали HTTP, SQL, файлов |
| `src/<package>/adapters/` | внешние системы: HTTP, БД, файлы, сторонние API | доменные решения |
| `src/<package>/models/` | контракты данных, схемы конфигурации, публичные типы | бизнес-логика |
| `src/<package>/utils/` | небольшие помощники без доменного знания | правила продукта |
| `src/<package>/llm/` | вызовы моделей, токенайзеры, повторные попытки | бизнес-промты без ссылки на ТЗ |
| `src/<package>/browser/` | Playwright/Chrome, сессии, cookies, скриншоты | парсинг конкретного сайта как бизнес-сценарий |
| `src/<package>/plugins/` | необязательные расширения с явным интерфейсом | ломать базовую работу без плагина |

Правило зависимостей:

```text
app → use_cases → core
use_cases → adapters
adapters → models
core → models
```

`core` не знает про `adapters`, `plugins`, `browser`, `llm` и `app`.

## 4. Профили проекта

Стандарт описывает не одну форму на все случаи, а набор разрешённых профилей.
Профиль выбирается по фактической природе проекта и фиксируется в
первых строках `structure.txt`.

ТЗ на структурную адаптацию объясняет отклонения и план миграции, но не
заменяет запись профиля в `structure.txt`.

| Профиль | Когда применять | Кодовая структура | Что остаётся общим |
|---------|-----------------|-------------------|--------------------|
| Одиночный Python-проект | новый сервис или библиотека в одном пакете | `src/<package>/...` | корень, `docs/`, `tests/`, `configs/`, `tools/` |
| Переходный Python-сервис | существующий большой сервис, где перенос импортов рискован | временно допускаются корневые `app/`, `core/`, `models/`, `utils/`, профильные папки | общий минимум + ТЗ на миграцию |
| Многомодульный проект | несколько независимых пакетов или сервисов в одном репозитории | `modules/<name>/`, `packages/<name>/` или `services/<name>/`; внутри каждого модуля свой профиль | общий `docs/`, `tools/`, `configs/` при необходимости |
| Рабочая область продукта | несколько разных поставок рядом: сервис, расширение, демо, издания | явные папки продуктов или сервисов; у каждой своя внутренняя структура | общий `docs/`, входы агентов, реестры |
| Продуктовая платформа | один большой продукт с backend, frontend, данными, поставкой и подпроектами | доменные папки продукта + `src/` или корневые пакеты; подпроекты могут иметь свой профиль | общий `docs/`, `tests/`, `scripts/`, `configs/`, `data/`, `logs/` |
| Плоское Python-приложение | старый прикладной проект с несколькими `.py` в корне | корневые `.py`, `requirements.txt`, `static/`, `templates/`, `data/` при необходимости | общий минимум + ТЗ на постепенный перенос |
| ML-лаборатория | эксперименты, датасеты, модели, результаты прогонов | `datasets/`, `models/`, `runs/`, `results/`, `notebooks/`, `src/` или `project/src/` | отчёты, описание данных, правила хранения артефактов |
| Локальная утилита | маленькая программа или скрипт для личной/операторской задачи | один или несколько `.py`, `requirements.txt`, локальные входные файлы | полный скелет не нужен; нужен `README.md`, если утилита живёт долго |
| Расширение браузера | Chrome/браузерное расширение | `manifest.json`, `background/`, `content*.js`, `popup.html`, `icons/` | `docs/`, `package.json`, материалы сборки |
| Сайт или клиентская веб-область | сайт, бренд, SEO, фото, дизайн, прототипы | папки клиента/сайта, `БТ/`, `Дизайн/`, `SEO/`, `фото/`, прототип | `docs/` или явная карта материалов |
| Внешний исходник | скачанный или заимствованный проект, который не наш основной код | исходная структура источника сохраняется | запись об источнике, версия, список локальных изменений |
| Железо и прошивки | Arduino, платы, датчики, прошивки | папки плат и датчиков, `.ino`, схемы, измерения | инструкция сборки и подключения |
| Восстановление медиа | разбор носителя, извлечение видео/аудио, временные кадры и восстановленные файлы | `tools/`, `docs/`, папки исходных носителей, `tmp_frames/`, результаты восстановления | не смешивать инструменты и тяжёлые артефакты |
| Закрытое хранилище | credentials, ключи, локальные системные сведения | минимальная структура, часто без документации | не валидируется как рабочий проект, не публикуется |
| Инфраструктурный проект | сеть, окружения, инструкции, shell/Python-скрипты без единого пакета | доменные папки вроде `tailscale/`, `assistants/`, `shared/`, `scripts/` | `docs/`, `structure.txt`, словарь терминов |
| Библиотека и мастерская | проект, который хранит стандарты, промты, скилы и шаблоны для других проектов | `_architect/`, `_library/`, `_workspace/`, `docs/memory/` | корневые входы, индекс библиотеки, словарь терминов |
| Frontend | структура фреймворка: `src/`, `public/`, `app/` при необходимости | структура фреймворка | `docs/`, `AGENTS.md`, `structure.txt`, `docs/ТЕРМИНЫ.md` |
| Один скрипт | маленькая утилита без длительной жизни | `script.py`, `README.md`, `requirements.txt` или `pyproject.toml` | полный скелет не нужен |
| Архив или резервная копия | старые версии, бэкапы, выгрузки, временные результаты | исходная структура сохраняется | не валидируется как рабочий проект |
| Справочная коллекция | статьи, сведения, тендерные базы, Obsidian-материалы | тематические папки и файлы | достаточно карты или README при долгой жизни |

Переходный Python-сервис — не целевое состояние. Он нужен, чтобы не ломать
живой проект переносом импортов. Новые крупные модули в таком проекте
добавляются уже по целевой схеме или с явной записью в ТЗ.

Если профиль отличается от стандарта, причина фиксируется в:

```text
docs/ТЗ/01_ТЗ_структурное_исключение__DONE.md
```

Если проект временно остаётся в переходном профиле, вместо `__DONE`
используется `__TODO` или `__WIP`, пока перенос не завершён.

### 4.1. Продуктовая платформа

`product_platform` применяется к большим живым продуктам, где рядом могут
существовать backend, frontend, данные, инструменты поставки и несколько
подпроектов.

Правила мягкой миграции:

1. Не переносить существующие папки ради красоты, если это ломает импорты,
   запуск или историю Git.
2. В `structure.txt` фиксировать профиль и краткую карту верхнего уровня.
3. В `docs/ТЗ/01_ТЗ_структурная_миграция__TODO.md` или
   `docs/ТЗ/01_ТЗ_структурное_исключение__DONE.md` описывать, почему проект
   временно отличается от целевого профиля.
4. Новые крупные части добавлять уже явно: `frontend/`, `services/<name>/`,
   `modules/<name>/`, `packages/<name>/` или доменная папка продукта.
5. Общие контракты, переменные окружения и публичные точки входа описывать в
   `docs/registry/` или в ближайшем существующем разделе документации.
6. Если есть веб-интерфейс, обязательно вести `docs/Дизайн/` и ссылаться на
   `WEB_INTERFACE_STYLE_STANDARD.md`.

Цель профиля — не немедленно привести большой продукт к одному виду, а сделать
его читаемым, проверяемым и безопасным для постепенных изменений.

### 4.2. ML-лаборатория

`ml_lab` применяется к экспериментам, датасетам, моделям и результатам
прогонов.

Правила хранения:

1. В Git хранятся код, конфигурации, маленькие примеры данных, описания
   датасетов, отчёты и команды воспроизведения.
2. Тяжёлые данные, модели, кеши и результаты прогонов хранятся вне Git:
   `data/`, `datasets/`, `models/`, `runs/`, `results/`, `artifacts/`.
3. В каждой тяжёлой папке допустим `README.md` с описанием, откуда взять
   данные и как проверить их версию.
4. Для важных прогонов фиксируются: конфигурация, дата, версия данных,
   параметры модели, метрики и путь к артефактам.
5. Секреты, токены и приватные клиентские данные не попадают в Git даже в
   обезличенных примерах без явного решения человека.

Минимальный индекс лаборатории:

```text
docs/README.md
docs/ТЕРМИНЫ.md
docs/Отчеты/
configs/
scripts/ или src/
```

### 4.3. Сайт или клиентская веб-область

`site_workspace` применяется к папкам, где рядом лежат БТ, ТЗ, дизайн, SEO,
фото, прототипы и материалы публикации сайта.

Канон верхнего уровня:

```text
README.md
structure.txt
docs/ или явные разделы БТ/, ТЗ/, Дизайн/
SEO/
фото/
uploads/        # если нужны исходные клиентские материалы
prototype/      # если есть отдельный прототип
```

Правила:

1. `README.md` объясняет, что это за сайт, где текущий источник правды и что
   публикуется.
2. БТ, ТЗ и дизайн не смешиваются с фотографиями и выгрузками.
3. SEO-материалы ведутся отдельным разделом, но ссылки на страницы и офферы
   должны совпадать с ТЗ и дизайном.
4. Если сайт становится полноценным приложением с `package.json`, `src/`,
   сборкой и тестами, профиль меняется на `frontend` или `product_platform`.
5. Для рабочих веб-интерфейсов применяется `WEB_INTERFACE_STYLE_STANDARD.md`.

## 5. Правило глубины

По умолчанию не уходим глубже второго уровня для управленческих материалов.

Разрешённые исключения:

- `src/<package>/<module>/...` — кодовая модульность;
- `docs/<раздел>/<файл>` — документация;
- `tests/<вид>/<файл>` — `unit`, `integration`, `contract`, `e2e`;
- `.claude/skills/<skill>/` и похожие папки инструментов;
- структура, которую требует фреймворк.

Нельзя создавать управленческие лабиринты:

```text
docs/ТЗ/управление_проектом/разработка/tasks/<feature>/
scripts/old/manual/tmp/
reports/audits/2026/may/final/
```

Такие материалы становятся плоскими файлами с номером и статусом:

```text
docs/ТЗ/30_ТЗ_<feature>__TODO.md
docs/Отчеты/30_Отчет_<feature>_аудит__DONE.md
```

## 6. Именование

### Файлы

- Python: `snake_case.py`
- TypeScript: `kebab-case.ts`, React-компоненты `PascalCase.tsx`
- Markdown-стандарты: `SCREAMING_SNAKE.md`
- Документы проекта в `docs/`: `NN_ТИП_тема__STATUS.md`
- YAML/TOML: `kebab-case.yaml`
- Тесты: `test_<module>.py` / `<module>.test.ts`

### Каталоги

- Одно слово или `snake_case`: `use_cases/`, `adapters/`, `docs/`
- Не использовать смешанный стиль: `CoreLogic/`, `utils-helpers/`
- Множественное число — для коллекций: `adapters/`, `models/`, `plugins/`
- Единственное — для единого слоя: `core/`, `app/`

### Статусы

`NN_...__STATUS` применяется к:

- `docs/БТ/*`
- `docs/ТЗ/*`
- `docs/Дизайн/*`
- `docs/Инструкции_пользователя/*`
- `docs/Инструкции_разработчика/*`
- `docs/Отчеты/*`

Не применяется к:

- исходному коду;
- тестам;
- конфигурации запуска;
- JSON/YAML-manifest;
- сгенерированным результатам.

Статус реализации кода определяется ТЗ, а не именем файла.

## 7. Что в Git, что нет

### В Git

- `src/`
- `configs/`
- `scripts/`
- `tools/`
- `tests/`
- `docs/` кроме `docs/_build/`
- `deploy/`, если он есть
- входные файлы: `README.md`, `AGENTS.md`, `CLAUDE.md`, `QWEN.md`,
  `structure.txt`, `pyproject.toml`, `.gitignore`
- общие настройки агентов, если они не содержат локальных секретов

### Не хранится содержимым в Git

- `data/`
- `logs/`
- `artifacts/`
- `build/`
- `docs/_build/`
- `.env`, `*.local.*`
- `__pycache__/`, `.pytest_cache/`, `node_modules/`
- секреты, приватные ключи, лицензии конкретной машины

Папки `data/`, `logs/`, `artifacts/` могут содержать `README.md`, чтобы роль
папки была видна в пустом проекте.

## 8. Защищённая поставка

Если проект поставляется клиенту как бинарь, он дополнительно подчиняется:

```text
_library/delivery/DELIVERY_ARCHITECTURE_CHECKLIST.md
```

Требования к структуре:

1. Чувствительная логика живёт в `src/<package>/core/`,
   `src/<package>/use_cases/`, `src/<package>/llm/`,
   `src/<package>/plugins/`, `src/<package>/browser/`.
2. Точки запуска в `src/<package>/app/` остаются тонкими.
3. Граница License Hub одна: обычно `src/<package>/adapters/license/` или
   `src/<package>/plugins/license_client/`.
4. Схема конфигурации живёт в `src/<package>/models/config_schema.py`.
5. Профиль поставки — `configs/delivery.yaml`.
6. Изменяемое состояние — `data/`, `logs/`, `artifacts/`, снаружи бинаря.

## 9. Проверка

На каждом проекте:

1. `docs/dev/standard/tools/validate_structure.py --profile auto` проверяет
   обязательный минимум с учётом профиля проекта. Инструмент приезжает
   вместе со стандартом и знает свою версию; самодельной копии в `tools/`
   проекта быть не должно.
2. `structure.txt` содержит строку `Профиль структуры: <profile>` и
   обновляется после изменения папок.
3. `README.md` содержит раздел `Запуск` и строку `Основной запуск:`, а
   глаголы раздела взяты из таблицы §2.1. Проверяется флагом
   `--check-launch-section`. **Пока флаг не реализован, пункт закрывается
   ревью, а не инструментом**: проверка, добавленная 13.06.2026, жила в
   форке валидатора внутри шаблона проекта и исчезла вместе с ним — в
   выпуске 2.9.173 её нет ни в одной копии. См.
   `docs/ТЗ/13_ТЗ_унификация_запуска_и_презентаций__TODO.md`.
4. Незакрытая работа видна через:

   ```bash
   ls docs/ТЗ/*__TODO.md docs/ТЗ/*__WIP.md docs/ТЗ/*__BLOCKED.md
   ```

5. Сознательное отклонение фиксируется в
   `docs/ТЗ/01_ТЗ_структурное_исключение__DONE.md`.
